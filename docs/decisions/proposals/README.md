# D03 schema draft bundle (GammaRay v0.0.2)

**Not a production schema.** The owner approved the native JSON Schema Draft 2020-12 approach and the addition of `software_inventory` and `vulnerability`, but approval of the complete observable field model is still pending. Task **P0-D03-002** (this revision) corrected the finding identity contracts, the observable classifications, and the supporting-evidence contract, and approved the two numeric caps (32 CVEs per event; 64 `raw_ref` values per observation). It did not approve the complete field model, and nothing here is implemented application code.

Files:

- `D03_NORMALIZED_EVENT.schema.json`: common envelope and 11 event-family alternatives.
- `D03_SOFTWARE_INVENTORY.schema.json`, `D03_VULNERABILITY.schema.json`: two separate family constraints. They are **referenced by `$id`** from the root. Load all three schemas into a local 2020-12 resource registry before validation; do not attempt network resolution of `urn:gammaray:*` identifiers.
- `D03_OBSERVABLE_REGISTRY.json`: **registry version 2** — 26 leaf fields, each declaring type, limits, handling class, permitted event families, required/nullable status, validation rules, and normalization behavior. Every `host`, `actor`, `network`, `web`, `process`, `file`, `software`, and `vulnerability` field must have exactly one corresponding entry. Only `operational` and `sensitive` observables may be normalized. Handling classes were corrected under P0-D03-002: public values (CVE identifiers, CVSS scores, public software vendor/name/version, CPE, purl, protocol) are `operational`; host/asset identifiers, account identifiers, and asset-linked statements (including `vulnerability.source_finding_id`) are `sensitive`; raw messages and unrestricted free text are `restricted` and never appear here. The registry's `classification_policy` records the value-versus-association rule and the escalation rule for internal/proprietary identifiers.
- `D03_FINDING.schema.json`, `D03_FINDING_OBSERVATION.schema.json`: **proposed** derived-record contracts (D03 §9). A finding is not a normalized event. State findings key on scope + rule id + canonical subject; occurrence findings add a deterministic occurrence key; observations carry rule/parser/feed provenance, the evidence-set hash, and 1–64 unique `supporting_raw_refs`.
- `D03_example_*.json`: synthetic fixtures. `D03_example_finding_identity.json` carries the deterministic identity **test vectors** for the v2 models (plus the retired v1 vector, labeled, for migration reference); `D03_example_finding.json` and `D03_example_finding_observation.json` are record fixtures for the two proposed derived-record schemas. The finding fixtures are **not** normalized-event fixtures.

Runtime validators must enable assertion checks for RFC3339 `date-time`, IPv4/IPv6 addresses, and URI formats; a JSON Schema implementation that silently ignores `format` is insufficient. Application-level parsers must also enforce the source/producer mapping, actual DNS/URL semantics, control characters, sensitive path content, canonical digest casing, cross-field timestamp consistency, and deterministic IDs. Do not treat syntactic acceptance as proof a scanner report is genuine or a software version is affected by a CVE.

A software-inventory event identifies **one** source-reported software item; a vulnerability event proposes **1–32 distinct CVEs** for a single source observation. If a source raw record has 33 or more CVEs or multiple inventory products, preserve it in the protected raw tier and quarantine the attempted normalized projection with a typed reason. No implicit fan-out, splitting, or silent truncation is authorized. The same no-truncation rule binds finding observations: an evidence set above 64 references quarantines the observation with `EVIDENCE_SET_TOO_LARGE` (D03 §9.3). Future source-specific fan-out requires an additional owner decision and a change to event identity rules.

Inventory coverage is not guaranteed by Splunk/CSV transports or occasional Windows/macOS install events. D04 must approve explicit inventory and scanner CSV mappings; D06 must approve and validate the inventory source, scanner feed, CVE feeds, revision and staleness policy before a coverage claim is made. Reliable vulnerability correlation requires actual software inventory or vulnerability scanner feeds; ordinary Windows, macOS, or network logs do not provide complete inventory.

The root schema's proposed `schema_version: 1` has not been published or implemented. The resource `draft-2` identifier tracks the design revision only. A reviewer can repeat fixture and contract validation using Python `jsonschema` 4.x (with `referencing` where available) via `docs/evidence/D03_draft_contract_check.py`; test evidence is in `docs/evidence/PHASE0_V002_VERIFICATION.md`. Node 24 runtime validators and generated TypeScript remain future P1/2 work: the contract is kept consistent by the registry↔schema checks and the executable contract suite, and TypeScript generation must be verified against these schemas when it is introduced.
